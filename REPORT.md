# Отчёт: распределение дефицита

**Правило.** Приоритет жёсткий: уровень 1 обслуживается раньше уровня 2. Внутри уровня объём
раздаётся по одной партии: следующую получает заявка с наименьшей долей `allocated / demand`,
ничья решается по `request_id`. Первая партия заявки равна `min_shipment_qty` (min_lot, поднятый
до кратности), следующие равны шагу кратности. Проходов два: первый отгружает не больше `demand`
с округлением вниз, второй раздаёт только остаток и может округлить вверх до кратности.

## 1. Журнал решений

| Развилка | Выбрано | Отвергнуто и почему |
|---|---|---|
| Приоритет и пропорция | Жёсткие уровни, внутри уровня партия идёт самому недообеспеченному. Итог близок к пропорции, min_lot соблюдается сам | **Мягкий вес**: веса нужно подбирать, бизнесу сложно объяснить. **Явная пропорция**: в CASE_02 даёт по 25 при min_lot 30, нужен итеративный пересчёт |
| Остаток, который не подходит старшему уровню | Отдаётся младшему | Держать ради старшего: товар простаивает |
| Перегруз | Только из остатка во втором проходе, меньше одной партии | **Никогда**: в CASE_05 на заводе лежит 440 шт., получатели недополучают до коробки. **Всегда вверх**: при дефиците отнимает объём у других |
| Ничьи | `(доля, request_id)`, доля через `Fraction` | Порядок строк: CASE_04 перемешан, план зависел бы от выгрузки |
| Некорректные данные | Схема pydantic отклоняет строку: заявка получает 0 с причиной в логе, кейс считается дальше. `rounding_value=0` = «без кратности», как `min_lot=0` | Ронять прогон: одна строка блокирует план всей сети |

## 2. Проблемы во входных данных и постановке

- **R-302: `demand_qty=-10`.** Отклоняется схемой. R-301 с `demand_qty=0` ошибкой не считается.
- **R-304: `rounding_value=0`.** Смысл не определён, может быть и деление на ноль. Трактуется как 1, в логе предупреждение.
- **R-602: `min_lot=250`.** Больше спроса и больше доступного, отгрузка невозможна. Заявка получает 0 с предупреждением, похоже на ошибку мастер-данных.
- **R-601: `min_lot=30` не кратен 25.** Порядок применения ограничений не задан. Выбрано: минимум 50.
- **Перегруз в постановке не определён.** Канала для предупреждений в сигнатуре `allocate` нет, поэтому отказы собираются при чтении CSV.

## 3. Три вопроса аналитику

1. **Допустимо ли полное голодание младших приоритетов** (CASE_07: 100/0/0)? Если нет, нужен гибрид с гарантированным минимумом, а это другое ядро.
2. **Что важнее при min_lot: охват точек или полнота отгрузки?** В CASE_02 это 40/30/30/0 или 50/50/0/0. Сейчас выбран охват.
3. **Допустим ли перегруз и в каких пределах?** От ответа зависит, останется ли второй проход и какой у него потолок.

## 4. Границы применимости

- **Жёсткий приоритет** оставляет младших без отгрузки (CASE_07).
- **Ничья по `request_id`** в многопериодном прогоне каждый раз ущемляет одну и ту же точку (R-204).
- **Пропорция по спросу** поощряет завышенные заявки.
- **Жадная выдача первых партий** не оптимальна как упаковка: при крупных min_lot разного размера остаток может пропасть.
- **Время растёт с числом партий.** Замер: 5 заявок по 2000 шт. с кратностью 1 считаются 23 мс, в 250 раз дольше кейса из CSV.

## 5. Масштаб: 5 млн кейсов за ночь

Замер текущей реализации: около 90 мкс на кейс из CSV, то есть примерно 7–8 минут на 5 млн
кейсов на одном ядре. При крупных объёмах с мелкой кратностью (23 мс на кейс) получились бы
десятки часов, поэтому:

1. **Алгоритм.** Цикл по партиям заменить закрытой формулой для каждого уровня: доли
   пропорционально спросу в целых партиях, затем исключение заявок ниже `min_shipment_qty`
   с пересчётом, затем остаток методом наибольшего дробного остатка. Время перестаёт зависеть
   от объёма. Текущая версия остаётся эталоном для сверки в тестах.
2. **Векторизация.** Закрытую формулу можно считать сразу по всем кейсам в numpy или polars
   с группировкой по `(case_id, priority)`. На 3–5 заявках numpy ничего не даёт, поэтому
   в ядре его нет.
3. **Выполнение.** Кейсы независимы. Пул процессов по чанкам, потоковое чтение из БД или
   parquet, пакетная запись. Ошибка одного кейса не останавливает ночной прогон.

## 6. Многопериодность

Жадное распределение оптимизирует каждый период отдельно, а уровень сервиса считается по всему
горизонту:
- объём, отданный в t младшему приоритету, может понадобиться в t+1 под крупный заказ старшего;
- точка, которая систематически проигрывает ничью или min_lot, копит перенесённый спрос без
  предела;
- перегруз в t уменьшает доступное в t+1.

Что бы я делал, от простого к сложному:
1. Считать долю удовлетворения накопительно, с учётом бэклога. Кто недополучил вчера, получает
   первым сегодня.
2. Резервировать объём под известный приоритетный спрос на 1–2 периода вперёд.
3. Решать задачу на скользящем горизонте как LP/MIP, фиксировать только первый период. Эвристика
   остаётся быстрым fallback и стартовым решением.
